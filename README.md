# 录音棚跳线盘路由规划器

一个跳线盘（Patchbay）路由规划网页应用：配置设备端口、背板连接与常态模式，
指定若干条“信号源 → 目标设备”的路由，系统自动计算**前面板最少跳线方案**，
正确处理插头对常态连接的断开规则，检测反馈环路，并在页面上绘制信号链、
列出接线顺序；无解路由会标明冲突端口。

新增 **单点故障评估（断路演练）** 模块：完成规划后，可任选一条**已安装跳线**
或一条**生效中的常态连接**模拟断路，后端在保持其他占用状态不变的前提下重新评估
全部路由，列出受影响路由、失效原因、断点端口与仍可用的替代路径；候选断点按
受影响路由数量降序排列。

新增 **前面板走线排版** 模块：完成规划后，用户为面板分区指定**可用走线槽层**
与**固定插孔列位**；系统保持信号拓扑、常态模式与跳线端点不变，为每根跳线分配
**走线层**与**左右绕行方向**，按「交叉数最少 → 跨区线数最少 → 同层长度最短」
字典序求解，输出每根跳线的层/方向、交叉对与无法避免的冲突；页面展示优化前后
指标与可缩放面板走线图。

新增 **信号命名一致性审计** 模块（`POST /api/signal-audit`）：用户为设备端口、
插孔对、已规划跳线与路由填写**规范信号名**及**别名**；系统沿设备内部、生效常态
与已安装跳线传播名签，按**半常态分流语义**归并端点，检测：

- **互斥名称（mutex）**：同一物理连通分量上出现多个规范信号名；
- **别名环（alias-ring）**：别名指向成环（`cycle`）或同一别名被指向多个规范名
  （`diverging` 分叉）；
- **无标签断点（unlabeled）**：承载路由信号的跳线源端、以及半常态上插孔插线
  的并送分流点没有任何名签；
- **跨路由串线（crosstalk）**：来自**独立信号源**（与名签无关）的已规划路由在
  同一物理连通分量汇合。信号源身份即路由源端口：同源端口、反馈环中互达的源端口
  合并为一个独立源；审计还会从路由源沿设备内部、生效常态与跳线**反向追溯共同
  上游**——一个真实信号进入多输出设备后从两个输出端口分别建立路由（或被常态 /
  跳线推动出的多条支路）只算该独立源的**同源分支**，归为同一来源、不计串线；
  只有反向终源互不相同的多源混合（含调音台混合输出、半常态并送汇合）才报警。
  **改名 / 改别名不会消警**，只有调整路由规划或物理连通后重新规划才能消除。

每个问题都给出**多源 BFS 最短证据路径**（port/edge 交替，含设备内部 / 常态 /
跳线各跳）、**可采纳规范名**（分量内声明次数最多，并列取字典序最小）与一组
**修正预览**（把落败名降级为别名的 `rename`、补名签的 `add-label`、剪断环边的
`break-alias`）；**跨路由串线不提供可消警的改名操作**，只返回物理处置提示，复审
时仍高亮同一条物理证据路径。审计**只读取规划结果，不修改任何路由 / 常态 / 跳线**；
页面按连通分量着色拓扑，点击问题高亮其最短证据路径，可逐条采纳修正预览并即时复审。

- 后端：Python Flask（`app.py` + 纯逻辑求解器 `solver.py`）
- 前端：原生 HTML / CSS / JavaScript（`static/`）

## 快速开始（Docker，单条命令）

```bash
docker compose up --build
```

启动后在浏览器访问：**http://localhost:8000**

## 本地开发（不用 Docker）

```bash
pip install -r requirements.txt
python app.py
```

同样访问 **http://localhost:8000**。

## 使用说明

1. **设备与端口**：登记每台设备的输入/输出端口（逗号分隔）。
2. **插孔对与背板连接**：每对插孔包含上插孔 `编号T`（背板接设备输出）与
   下插孔 `编号B`（背板接设备输入），并选择常态模式：
   - **全常态（full）**：上/下插孔任意一侧插入插头即断开常态连接；
   - **半常态（half）**：仅下插孔插入断开常态；上插孔插入时常态保持、信号并送（可监听/分流）；
   - **直通（through）**：上下插孔之间无常态连接。
3. **路由请求**：按顺序指定多条“输出端口 → 输入端口”的路由。
4. 点击 **计算路由方案**，页面展示：
   - 最少跳线数量与**接线顺序**；
   - 每条路由的**信号链**（常态 / 设备内部 / 跳线逐段展示）；
   - **前面板跳线图**（生效/断开的常态、跳线走线）；
   - 插头对常态连接的影响说明；
   - 无解路由的**冲突端口**（插孔被占用、常态被保护等）；
   - **反馈环路**警告（信号经设备与连线形成回路时）。

右上角下拉框可载入五个内置示例：标准录音链（可解）、冲突演示（无解）、
反馈环路演示、走线排版演示（多分区 + 交叉优化）、命名审计演示（四类命名问题）。

## 单点故障评估（断路演练）

1. 先点击 **计算路由方案** 完成一次正常规划；规划结果里的所有**已安装跳线**
   与**生效中的常态连接**会进入“4. 单点故障评估”卡片的下拉清单，并
   **按受影响路由数量降序排列**（数量相同时跳线在前、再按编号）。
2. 选择一个断点后点击 **🔌 断路演练**，后端会：
   - 摘除该跳线（释放其两端插孔）或将该常态连接强制切断，**其余跳线与
     常态占用一律保持不变**；
   - 按原路由顺序对受影响路由重新求最短路（只允许使用当前空闲插孔插入
     新跳线，不改动任何仍在服役的连接）；
   - 返回受影响路由、失效原因、**断点端口**（如 `3T / 3B`）、仍可用的
     **替代路径信号链**、需要新增的跳线与替代接线顺序，以及断路后的面板图；
   - 未受影响路由原样列出（沿用原跳线/常态）。
3. 结果区按“失效路由优先、其后按路由编号”排序；页面底部给出所有断点的
   单点故障排序总表。

演练语义说明：不存在全局重排——替代路径必须与其余仍在服役的路由共存
（与原规划一致的逐条贪心模型）；若某条路由在其他占用不变时确实无路可走，
接口返回 **409** 结构化结果，完整评估数据仍在响应体的 `assessment` 字段中。
注意：半常态（half）插孔在上插孔插线时信号并送，多个路由可共享同一条常态，
因此同一次断路可能同时影响多条路由。

## 前面板走线排版

完成一次 **计算路由方案** 后，“5. 前面板走线排版”卡片出现（规划无解时仍可对
已安装的跳线排版）。为每个分区填写：

- **插孔列位**：该分区内插孔对编号，按从左到右的物理顺序填写；所有插孔对必须
  且只能属于一个分区（后端校验，漏列/重列/未知编号都会 400 报错）；
- **可用走线槽层**：整数编号列表，如 `1, 2`；也可带容量 `1:6, 2:4`
  （每层每分区容量默认 8）。槽层深度按首次出现顺序确定，编号越小越靠近面板。

点击 **🧵 计算走线排版**，后端先复用既有规划（**信号拓扑、常态模式、跳线端点
完全不变**），再做排版：

- 跳线从上行 T 插孔垂入走线槽，水平走到下行 B 插孔后升起；跳线水平跨度经过的
  每个分区都必须提供同一槽层（**公共槽层**），并占用各分区该层 1 个容量；
- 为每根跳线分配槽层与**左右绕行方向**（决定从哪一侧进入相邻列槽隙）；
- 优化目标按字典序：**交叉数最少 → 跨区线数最少 → 同层长度最短**；
- 同层相邻列跳线的进槽方向对撞通过方向调整消除（不算冲突），反向绕行有 0.5
  列距的长度附加；
- **无法避免的冲突**：无公共槽层或容量已满导致的跳线未分配；以及受公共槽层/
  容量限制、改层也无法减少交叉的残留同层交叉（逐对给出交叉跳线号、槽层与
  `unavoidable` 判定）。

页面输出：优化前（贪心基线）/ 优化后的**指标对照表**（交叉数、跨区线数、
同层总长度、方向对撞、未分配跳线）、**每根跳线的走线方案表**（层/方向/长度/
是否跨区/状态）、冲突清单与**可缩放面板走线图**（±/复位缩放，槽层容量、
绕行方向、红色 ✕ 交叉点、红色虚线未分配跳线均有标注）。

> 关于“跨区线数最少”：分区列位由用户固定后，一根跳线是否跨区只取决于其两个
> 端点，因此该指标在排版过程中是**定值**，仅在交叉数并列时作为次序参考；它仍
> 是求解顺序中的第二优先级并在前后指标中如实展示。槽层与容量受限时的首要目标
> 是把每根跳线都分配出去（未分配数最少），其次才是交叉数等三项。

## 信号命名一致性审计

完成一次 **计算路由方案** 后，“6. 信号命名一致性审计”卡片出现（规划无解时
仍可对物理图与已安装跳线审计）。四个标签页分别为**设备端口 / 插孔对 / 已安装
跳线 / 路由**填写名签，每行一个**规范信号名**与一个**别名**（均选填）。载入
“命名审计演示”示例会预填一套覆盖四类问题的名签。

点击 **🔎 运行命名审计**，后端先复用既有规划（不改动任何路由结论），再：

- 在「设备内部 + 生效常态 + 已安装跳线」**无向物理图**上求连通分量；
- 把名签沿边传播：规范名落到端口；**别名按“别名 → 规范名”声明构造有向图**
  解析（纯别名端口在唯一收敛时按目标规范名补全）；
- 按**半常态分流语义**归并：半常态上插孔插线时常态保持、信号并送，上/下端口
  仍属同一分量，该点额外视为需要命名的**分流点**；
- 输出四类问题，每条含 `severity`、`component`、涉及名称 `names`、
  `suggestedName`（串线无此字段）、`evidence`（最短证据路径）与 `fixes`
  （修正预览；串线为**空数组**，改由 `resolution` 给出物理处置提示）。

| 问题类型 | code | 含义 | 修正预览 |
| --- | --- | --- | --- |
| 互斥名称 | `mutex` | 同一连通分量有多个规范名 | `rename`：落败名降为别名，统一为建议名 |
| 别名环 | `alias-ring`（`subtype: cycle/diverging`） | 别名指向成环或一别名对多规范名 | `break-alias`：剪断环边并统一规范名 |
| 无标签断点 | `unlabeled`（warning） | 路由跳线源端 / 半常态并送分流点无名签 | `add-label`：沿用分量内唯一规范名补签 |
| 跨路由串线 | `crosstalk` | 来自**独立信号源**的已规划路由汇于同一物理分量（与规范名/别名无关） | **无 rename**：只能改路由规划或断开物理连通，复审仍高亮同一证据路径 |

页面输出：统计条（分量数与四类问题计数）、**问题清单卡片**（点击展开最短证据
路径与可逐条采纳的修正）、**按连通分量着色的审计拓扑图**（点击问题后黄色高亮
证据路径、红色描边冲突端点，常态 / 跳线 / 半常态并送均有图示）。采纳任一修正
只会回填上方名签输入框并**立即重新审计**，不会修改路由；也可一键清空名签。

> 审计是只读分析：它不改配置、不重路由、不写入任何状态，结果完全由当前
> `config` + `labels` 决定；可反复运行。原规划、断路演练与走线排版互不影响。

### 错误响应（结构化）

| 场景 | HTTP 状态码 | `error.code` |
| --- | --- | --- |
| 配置非法（设备/端口/插孔对/路由定义有误） | 400 | `CONFIG_INVALID` |
| 排版分区非法（漏列/重列/未知编号、槽层/容量非法等） | 400 | `LAYOUT_INVALID`（`details.missing` 列出漏列编号） |
| 断路目标非法（跳线不存在、常态未生效等） | 400 | `FAULT_TARGET_INVALID`（`details.available` 列出可演练断点） |
| 名签非法（未知端口/插孔对/跳线、路由序号越界、重复填写等） | 400 | `LABELS_INVALID` |
| 演练完成但存在无替代路径的路由 | 409 | `NO_ALTERNATIVE`（完整结果在 `assessment`） |
| 请求体不是 JSON 对象 / 缺少字段 | 400 | `BAD_REQUEST` |

## API

- `GET /` — 页面
- `GET /api/examples` — 内置示例配置
- `POST /api/plan` — 求解（原有规划流程，保持可用），请求体：

```json
{
  "devices": [{"name": "PRE", "inputs": ["in"], "outputs": ["out"]}],
  "pairs":   [{"id": 1, "top": "MIC.out", "bottom": "PRE.in", "mode": "half"}],
  "routes":  [{"source": "MIC.out", "target": "PRE.in"}]
}
```

返回跳线清单、接线顺序、每条路由的信号链、冲突与反馈环路，以及
`failurePoints`（可演练断点及其受影响路由数，已排序）。

- `POST /api/fault-drill` — 单点故障断路演练，请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "target": { "type": "normal", "id": 3 }
}
```

`target.type` 为 `cable`（已安装跳线，`id` 为跳线编号）或 `normal`
（生效常态，`id` 为插孔对编号）。200 响应包含 `affectedRoutes`
（`restored`：替代链/新增跳线；`unroutable`：失效原因与断点端口）、
`unaffectedRoutes`、`breakPorts`、`newCables`、`steps`、断路后的
`pairs` / `cables` / `feedbackLoops` 与 `failurePoints` 排序表；
409 时上述结构位于响应体 `assessment` 中。

- `POST /api/panel-layout` — 前面板走线排版，请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "layout": {
    "zones": [
      { "name": "左区", "columns": [1, 2, 3],
        "layers": [1, 2, {"id": 3, "capacity": 6}] }
    ]
  }
}
```

`columns` 是插孔对编号从左到右的物理列位（必须覆盖全部插孔对且不重复）；
`layers` 为该分区可用走线槽层，可写整数或 `{id, capacity}`（容量默认 8）。
响应包含：

- `zones`：各分区列位区间、槽层深度与 `used/capacity` 占用；
- `jacks`：每个插孔的列位/分区/端口（供绘图）；
- `cables`：每根跳线的 `layer`、`direction`（`L` 左绕 / `R` 右绕）、
  `directionLabel`、`fromCol/toCol`、`fromZone/toZone`、`crossZone`、
  `length`、`status`（`routed` / `unassigned`）与未分配原因；
- `crossingPairs`：优化后仍残留的同层交叉对（含 `unavoidable` 判定）；
- `conflicts`：无法避免的冲突（`unassigned` / `crossing`）及中文原因；
- `metrics.baseline` 与 `metrics.optimized`：优化前后的 `crossings`、
  `crossZone`、`length`、`gapConflicts`、`unassigned`；
- `planOk`（原规划是否全部可解）、`solverNote`（搜索超限时的回退说明）。

排版接口不改动任何路由结论：它内部复用 `POST /api/plan` 的同一规划流程，
原规划冲突时仍可对已安装跳线排版，并以 `planOk`/横幅提示。

- `POST /api/signal-audit` — 信号命名一致性审计（只读，不改路由），请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "labels": {
    "ports":  [ {"port": "MIC.out", "name": "VOX", "alias": "人声"} ],
    "pairs":  [ {"id": 1, "name": "VOX"} ],
    "cables": [ {"id": 2, "name": "VOX"} ],
    "routes": [ {"index": 0, "name": "VOX"} ]
  }
}
```

`labels` 的四个数组均选填，每项只需 `name`（规范信号名）与 `alias`（别名）
至少一个；`ports[].port` 为 `设备.端口`，`pairs/cables` 用编号 `id`
（cable 必须是当前规划已安装的跳线），`routes` 用从 0 起的 `index`。
插孔对 / 路由名签会同时挂到其两端端口。响应包含：

- `ok`：是否不存在 error 级问题（unlabeled 为 warning，不影响 ok）；
- `planOk`：底层规划是否全部可解；
- `summary`：`components` / `activeComponents`（承载路由的分量）/
  `labeledPorts` / `issueCounts`（四类计数）/ `issueTotal`；
- `components[]`：每个连通分量的端口（含插孔 `jack`、是否被命名 `labeled`）
  与归并出的 `canonicalNames`，供前端按分量着色；
- `issues[]`：`type`（mutex/alias-ring/unlabeled/crosstalk）、`severity`、
  `subtype`（alias-ring 的 cycle/diverging）、`component`、`names` /
  `conflictingNames` / `preferredName`、`suggestedName`、`routes`、
  `aliasChain`（环）、`evidence`（port/edge 交替的最短证据路径，每个 port
  带 `jack` 与该点 `names`，每条 edge 带类型与中文 label）、`fixes[]`；
  crosstalk 的 `fixes` 恒为 `[]`（改名不能消警），其 `names` 为两端独立源
  端口（与标签无关、供排序），另带 `sources`（两组独立源：`port`/`ports`
  /`originPorts`（反向追溯到的共同上游终源端口；同源分支可能与其直接源端口
  不同）/`routes`）、`routesBySource`（源端口 → 归属路由）、`downstream`（由多路
  并流形成的下游混合点，如调音台混合输出）与 `resolution`（仅物理处置提示）；
  同源多输出分支不会产生串线条目，复审时也不再提示改路由或断开这些分支；
  串线证据路径只随规划/物理连通改变，复审时保持不变。
- `fixes[]`：`action` 为 `rename`（`fromName→toName`，原名入 `alias`）、
  `add-label`（`name` 为建议补签名，可能为 null 需人工指定）或
  `break-alias`（删除 `removedAlias`、统一 `name`），均带 `target`
  （kind/id/index/port）与中文 `label`；crosstalk 不返回任何 fix。
- `pairs` / `cables` / `routes`：审计所基于的规划拓扑（供绘图与复核）。

## 求解模型

- 信号沿三类边流动：设备内部（输入→输出，0 跳线）、生效的常态连接
  （上→下，0 跳线）、前面板跳线（任意空闲输出插孔 → 空闲输入插孔，1 条跳线）。
- 按用户给定顺序逐条路由求解，每条在当前插孔占用状态下用 0-1 最短路
  （Dijkstra）求最少跳线路径；已提交路由占用的常态连接受保护，
  后续跳线不得将其断开（否则该插孔对后续路由禁用）。
- 路由失败时，对照“忽略占用”的理想路径定位被阻塞的边，报告冲突端口。
- 全部提交后，在“设备内部 + 生效常态 + 跳线”有向图上做 DFS 检测反馈环路。
- 断路演练复用同一图模型：摘除断点边/插孔占用后，仅释放“使用者全部为
  受影响路由”的常态保护（仍在服役路由依赖的常态继续保护），再按原顺序
  逐条重路由；新跳线编号单调递增，避免与保留跳线冲突。
- 走线排版复用 `plan_all` 的已安装跳线，只在面板几何层做分配：列位由分区
  声明确定；同一槽层内两根跳线的 T/B 列序互逆即为一次交叉（不同层物理
  错开不计）；跳线可用槽层 = 其水平跨度所经各分区槽层集合的交集，且受
  每层每分区容量约束。槽层分配用带剪枝的精确字典序搜索
  （未分配数 → 交叉数 → 同层长度，跨区线数为固定第二键），搜索规模超
  30 万节点时回退贪心并在 `solverNote` 说明；左右绕行方向在槽层确定后
  按层独立求解（相邻列进槽对撞最少、其次反向绕行附加最短，≤16 根时
  2^k 全枚举保证最优）。残留交叉再逐根试探改层，判定是否“无法避免”。
- 命名审计在 `plan_all` 完成后的**无向**物理图（设备内部 + 生效常态 + 跳线，
  边双向）上做并查集归并；半常态上插孔插线时不断常态，因此上/下端口仍在同一
  分量，并把该插孔对识别为需要名签的分流点。别名构造「别名 → 规范名」有向图，
  Tarjan 求 SCC 检测环（环代表取环内被显式声明为规范名次数最多、并列字典序
  最小者），同一别名多个出边检测分叉；纯别名端口在唯一收敛时按目标规范名补全。
  互斥名/无标签的证据路径用**多源 BFS** 求最短（所有同名端口同时为源、所有对方
  名签端口为汇），保证给出的是两个命名端点之间跳数最少的物理路径。
  **跨路由串线与名签解耦**：另建与 `detect_loops` 同构的有向信号流图
  （设备内部 in→out、生效常态 上→下、跳线 from→to），Tarjan 求 SCC 合并互达源
  （反馈环），再沿有向边**反向**追溯到缩点图上入度为 0 的**终源 SCC**（只含
  输入端口的悬空 SCC 不产生信号，仅在整段总线无驱动时按物理分量归为一个未接线
  来源）；源端口共享同一终源即为同一真实独立信号的**同源分支**（典型：真实
  信号进入多输出设备后从两个输出分别建路由），归为一个来源、不增加串线计数；
  一个源 SCC 反向追到多个不同终源才是真正的多源混合（覆盖设备内部混合与半常态
  并送），其路由归属全部终源。即使**只规划了混合输出**（例如路由列表仅含
  MIX.out→MON.in，两个真实源分别经生效常态进入 MIX.in1 / MIX.in2），审计也会
  从该混合源反向恢复两个真实独立源，把混合输出路由同时归属两源、照常返回一条
  串线（不会因混合点自身被归为 mix 而漏报），恢复出的源作为 `sources`、混合点
  列入 `downstream`，证据端点取两终源输出端口。同一无向物理分量内出现两个不同
  终源即报串线，证据路径为两组来源代表端口之间的多源 BFS 最短路（起点按端口名
  排序入队，保证可复现），只随规划/物理连通变化。
  审计全程不修改规划状态。
